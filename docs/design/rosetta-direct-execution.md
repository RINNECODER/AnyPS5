# Rosetta direct execution on Apple silicon (feasibility spike)

Status: spike, 2026-10-11. Prototype tooling is in [`tools/rosetta-spike`](../../tools/rosetta-spike) and [`tools/unself.py`](../../tools/unself.py). Nothing here changes the shipped runtime.

## Summary

Running guest code directly in an x86-64 process under Rosetta 2 is feasible on this fork, and most of the CPU side already exists upstream.

- Upstream's relinker already converts a title into an x86-64 Mach-O for Rosetta (`relinker --macos --to-rosetta`). The fork has this through the upstream sync. What upstream does not have is the macOS runtime that the output binds to. Those hooks are not implemented anywhere, and the system libraries do not build for macOS.
- With a ~150-line stub runtime, the reference retail title, relinked unchanged, ran natively under Rosetta. Both bundled guest modules' initialisers ran, the title's TLS was registered, the guest entry point was reached, and the guest made 633 import calls across 23 distinct NIDs. All of that took **56 ms of wall time from exec, warm**. It then stopped on a NULL dereference, because every import is a stub that returns 0. A cold first run takes 6.4 s, because Rosetta translates the 160 MB image ahead of time once and caches the result.
- On a guest-like integer, memory and scalar-FP loop, Rosetta ran **~4.7 G x86 instructions/s**. Block-chained QEMU TCG (Unicorn 2.1.4) ran ~0.75 G/s. The fork's single-stepping TCG path runs at ~16 MIPS (#125, #140, #141, #210). That puts Rosetta about **6x faster than the best TCG case and ~300x faster than today's path**. Native arm64 code was only 1.8x faster than Rosetta.
- The fork's Metal backend builds for x86_64 without changes, and its GPU tests pass inside a Rosetta process. Metal is therefore the realistic GPU backend. MoltenVK is not needed.
- The remaining work is porting the system libraries (`core/libs/prx`) to macOS x86-64 and writing the runtime hooks. A compile probe of the 41 CPU-side libraries the title links finds **27 failing translation units out of ~170**, all in `libc`, `libkernel`, `libSceFiber` and `libSceAudioOut`, with a short, known list of Linux-only APIs. The other libraries compile as they are.

Platform risk: Apple announced at WWDC 2025 that full Rosetta 2 stays available through macOS 27 (this machine runs it), and that later releases keep only a subset aimed at older games. This path depends on Rosetta staying available, so the TCG path has to remain as the fallback.

## 1. How upstream executes guest code

Upstream never interprets guest code. It relinks the guest ELF ahead of time into a native executable for an x86-64 host (see [ARCHITECTURE.md](../dev/ARCHITECTURE.md)):

- **Loader and relinker.** `core/relinker` reads the guest ELF and its bundled `sce_module/*` modules. It lowers AMD-only instructions with `--to-intel`, and with `--to-rosetta` it also turns RDSEED into RDRAND, CLWB into a NOP and RDPID into "processor 0". It checks for raw syscalls and writes an ELF (Linux), PE (Windows) or Mach-O (`--macos`) image.
- **Imports.** Each import is bound by NID to a host shared library, `libs/<name>.prx`, built from `core/libs/prx` with exports renamed to their NIDs by `nid_patcher`. On macOS the output uses classic `LC_DYLD_INFO` bind opcodes with flat lookup (21,270 binds over 1,757 distinct symbols for the reference title), plus one `LC_LOAD_DYLIB @rpath/<lib>.prx` for each of the 45 libraries.
- **Fixed mappings.** The Mach-O executable keeps the guest's segment layout at a fixed base. The reference title loads at `0x140000000` with `__PAGEZERO` extended below it. The output is not PIE (`MH_PIE` is clear), and the kernel and dyld mapped it under Rosetta without complaint.
- **FS-base TLS.** macOS cannot set `%fs`, so every `%fs:` access (about 2,000 sites in the reference title) is rewritten into a jump to a stub. The stub reads a per-image thread pointer from a pthread key (`%gs:[key*8]`, the Darwin TSD fast path). On a thread's first access it calls `Aps5GuestTlsAllocate` with the TLS descriptor in `%rax`. Only displacements inside the static TLS block, `0` (self pointer) and `0x28` (stack guard) are accepted. Dynamic TLS goes through the image's descriptor instead of `__tls_get_addr`.
- **Start-up.** `LC_MAIN` points at an entry stub that builds a FreeBSD-style `argc/argv/envp` frame and calls `Aps5StartGuest(entry, frame)`. Guest modules get a `__mod_init_func` that registers TLS, fetches module-start arguments through `__aps5_get_pending_module_args`, runs the module entry and reports the result.
- **Signals.** On macOS, the write watch (`libc/src/GuestWriteWatch.cpp`) and the register-context unwinder (`libc/src/specifics/x86_64/RegisterContext.cpp`) use SIGSEGV/SIGBUS and the Darwin x86-64 `mcontext`. Their standalone tests are built to run under Rosetta.

**How complete the macOS path is.** Only the relinker side is in the tree. `Aps5StartGuest`, `Aps5GuestTlsRegister` and `Aps5GuestTlsAllocate` have no implementation anywhere. [BUILD.md](../dev/BUILD.md) says the relinker-only mode "does not build those libraries or provide macOS game execution". [TechnicalDebt.md](../dev/TechnicalDebt.md) says "the macOS memory paths are not in the tree".

| Kernel and dyld load of the relinked image | OK. The fixed `0x140000000` base, 11 segments and flat binds all resolve |

**GPU backend: our Metal backend, built for x86_64.** Metal runs in Rosetta processes, and the backend compiles and passes its tests there. That covers the work already done on the fork: AGC submission, the SPIR-V to MSL bridge, presentation and guest-memory mapping. Upstream's Vulkan backend via MoltenVK would mean building Vulkan, glslang and SPIRV-Tools for x86_64 and adding another translation layer. It would also lose the Metal-specific fixes. One simplification applies: the guest pointer and the host pointer are now the same, so the borrowed guest ranges given to `MetalDriver::Configure` become plain host pointers. The TCG-side translation is not needed.

## 3. Rosetta-specific blockers and measurements

Run `tools/rosetta-spike/run_probe.sh <scratch>` to repeat these.

1. **Page size.** An x86_64 process sees `getpagesize() == vm_page_size == 4096`. `mprotect` on a single 4 KiB page inside a 16 KiB host page works. Writes to the neighbouring 4 KiB pages do not fault, and a write to the protected page faults once with the exact address. `MAP_FIXED` at 4 KiB-aligned addresses works. A `shm_open` object mapped at a 4 KiB file offset into a fixed 4 KiB slot is coherent with a second view, which is the direct-memory aliasing model. Native arm64 rejects all three of these (16 KiB granularity). PS5 direct memory uses 16 KiB pages (`PS5_PAGE_SIZE = 0x4000`), so granularity is not a blocker.
2. **Fixed guest address ranges.** Fixed mappings are refused with `EACCES` in **0x10_0000_0000–0x80_0000_0000 (64–512 GiB)**, both natively and under Rosetta. Below that (8–64 GiB) and from 512 GiB up, mappings work, and 64 GiB fixed reservations at 1 TiB and 126 TiB succeed. Upstream's `DirectMemory` already searches with `MAP_FIXED_NOREPLACE` up to `0x7fff00000000`, so it can avoid the hole. Only a title that asks for a fixed address inside 64–512 GiB would fail. The fix is the same as on other hosts: relocate or report.
3. **CPUID.** Rosetta reports a GenuineIntel family-6 CPU with SSE4.2, POPCNT and AES. It reports AVX, AVX2, FMA, BMI1/2, F16C, MOVBE, XSAVE/OSXSAVE and RDRAND as 0, but executes AVX2, FMA, BMI2 and F16C correctly (the `host_x86_avx2` build of the benchmark gives the same result). The reference title contains ~835k VEX-prefix bytes, so it is AVX code compiled for Zen 2. A byte scan finds ≤70 CPUID and ≤5 XGETBV sites (an over-count). Most console code uses AVX unconditionally and runs. Code that checks CPUID would take a slower path or refuse. The fix belongs in the relinker: rewrite CPUID sites into a stub that returns a Zen 2 profile, using the stub mechanism `--to-rosetta` already has (done; see "Start-up time and CPUID" in section 5). ADCX/ADOX fault under Rosetta. RDTSCP's `ECX` is the constant `0xAAAAAAAB`.
4. **x87 and AVX coverage.** Rosetta's x87 emulation is reported to compute in double precision, not 80-bit. This spike did not measure it. The microbenchmark's SSE and AVX builds give identical checksums across native, Rosetta and TCG, and no title-level x87 problem showed up within the spike's reach.
5. **Signals.** SIGSEGV/SIGBUS deliver the x86 `__ss.__rip` and the exact fault address under Rosetta. A protect-write-fault-unprotect round trip costs **~44 µs**. That is fine for guard pages, but expensive for a write watch that faults on every first write to a GPU-visible page. Batching or Metal-side dirty tracking will matter.
6. **System libraries do not build for macOS.** Configuring `tools/rosetta-spike/libs-probe` with `CMAKE_OSX_ARCHITECTURES=x86_64` and building with `ninja -k 0` gives these failures:
   - `libc` (10 TUs): ELF-only `.type sym, @function` in inline asm (setjmp, longjmp, getcontext) and `feof_unlocked`.
   - `libkernel` (13 TUs):
     - `link.h`/`dl_iterate_phdr`, which needs the dyld image APIs (`libc/src/specifics/macos/GuestImages.cpp` exists).
     - `sys/vfs.h`.
     - `memfd_create`, to be replaced with `shm_open` or `mach_make_memory_entry`.
     - `ppoll` and `POLLRDHUP`.
     - `RUSAGE_THREAD`, `sched_getcpu`, `pthread_getattr_np` and `pthread_getcpuclockid`, to be replaced with `pthread_get_stackaddr_np` and `thread_info`.
     - `st_atim` and friends, which are `st_atimespec` on macOS.
     - Linux `gregs` in `Exception.cpp`, which become `mcontext->__ss`.
     - `DirectMemory.cpp`, whose non-Linux branch is the Windows one.
   - `libSceFiber`: the same `.type` directive.
   - `libSceAudioOut`: needs SDL2.
   - All other probed libraries compile. `libHttpServer.Prospero` has no source directory, and `libSceAjm.native` and the graphics libraries need submodules (not probed).

## 4. Measurements

All runs were on an Apple M5 Pro running macOS 27. The kernel is [`tools/rosetta-spike/kernel.c`](../../tools/rosetta-spike/kernel.c): a hash, a dependent 16 KiB table load and store, and a branchy scalar double update. It is 22.5 x86 instructions per iteration, counted under Unicorn, and has no calls or literal pools, so its bytes run unchanged under TCG.

| Engine | Iterations | Time | Guest instr/s | Checksum |
| --- | --- | --- | --- | --- |
| Native arm64 build (reference) | 200 M | 0.529 s | n/a | `9f938a1e…` |
| Rosetta, x86_64 SSE build | 200 M | 0.949 s | **4.74 G** | `9f938a1e…` |
| Rosetta, x86_64 AVX2/FMA/BMI2 build | 200 M | 0.968 s | 4.65 G | `9f938a1e…` |
| QEMU TCG, block-chained, no hooks (Unicorn 2.1.4) | 20 M | 0.597 s | 0.75 G | `034e31c0…` (matches Rosetta at 20 M) |
| AnyPS5 TCG path today (single-step, #125/#140/#141/#210) | n/a | n/a | ~0.016 G | n/a |

The table shows Rosetta about 6x faster than the best TCG case, about 300x faster than today's single-stepping path, and 1.8x slower than native arm64 code.

Reference title milestones:

| Milestone | Rosetta direct (spike runtime, all imports stubbed) | TCG today (same day, same machine) |
| --- | --- | --- |
| Relink (one-time, cacheable) | 29 s | none |
| Runtime load to both guest module initialisers done | 7.6 ms (a cold image adds a one-time ~6.3 s Rosetta AOT translation before this) | not separately logged |
| Guest entry point reached | 3.6 ms warm / 8.1 ms cold after runtime load | not separately logged |
| First 633 import calls | within 16 ms of runtime load (56 ms wall from exec, warm) | not separately logged |
| First GPU submission / rendering | not reached (imports are stubs) | 1,628 s (smoke run today; 1,530 s earlier), one core at 100%, 13.8 GB peak RSS |

A rough projection: if the 1,628 s TCG boot is CPU-bound at ~16 MIPS, it is ~26 G guest instructions. At the measured 1–5 G/s, that work takes 5–25 s under Rosetta. The real figure will depend on how the libraries perform (file I/O, shader translation, memory mapping), not on guest instruction throughput.

The total is roughly 5–7 weeks of focused work to reach first rendering on the direct path. Phase 1 is the critical path. It is also the part most likely to bring upstream changes along, since upstream's own macOS runtime "comes in separate changes".

### Phase 2 status (runtime hooks)

- **Runtime.** [`core/libs/prx/libkernel/Darwin/GuestRuntime.cpp`](../../core/libs/prx/libkernel/Darwin/GuestRuntime.cpp) is built into the x86_64 `libkernel.prx` only. `Aps5StartGuest` builds a FreeBSD `argc/argv/envp/auxv` frame (`argv[0]` is `/app0/eboot.bin`, `AT_PAGESZ` is 16 KiB) and exits with the entry's result. Static TLS is per image and per thread, keyed by each image's pthread key and allocated on a thread's first access, so threads from `scePthreadCreate`, `pthread_create` or host libraries, and modules loaded later, all get every image's TLS. `Aps5GuestTlsGetAddr` serves guest `__tls_get_addr`. Blocks are freed when the thread exits.
- **Module order and loading.** dyld runs each image's `__mod_init_func` after its dependencies, so the bundled guest `libc` starts before the modules and the executable that import it. The relinker links `sce_module/*` as load-time dependencies. Modules under `--module-dir` are relinked but deferred, and `sceKernelLoadStartModule` `dlopen`s them with module arguments. Module ids now match `dlopen` handles on Darwin, because the loader records each handle's Mach-O header.
- **Faults.** SIGSEGV, SIGBUS, SIGILL, SIGFPE and SIGTRAP are reported from the moment `libkernel` loads. The report gives the fault address, `image+offset`, the guest address (`guest=`), the registers and a frame-pointer backtrace. The handler chains to the libc write watch first. Real faults are not yet delivered to guest exception handlers. `sceKernelRaiseException` keeps using the `__darwin_mcontext64` mapping from #394.
- **The 64–512 GiB hole.** Titles map at the start of the PS5 application area (`0x10_0000_0000`), which macOS refuses. Fixed requests that start in the hole are moved up by 448 GiB, to `[512, 960) GiB`, and the new address is returned through `*addr`. That keeps them below `0xFC_0000_0000`, which the guest libc checks pointers against. A request that starts below the hole and runs into it still fails with `ENOMEM`.
- **Running a title.** The engine launcher `anyps5_rosetta_run` (tools/rosetta/launcher, built into `<build>/rosetta/bin` with the libs; the engine package's executable, docs/RELEASES.md) unselfs and relinks the title, caches the result by eboot SHA-256 in `~/Library/Caches/AnyPS5/rosetta/<sha>/`, lays out `libs/` and `app0/`, and runs it. Libraries the build excludes get empty stand-ins. Imported NIDs that no library exports get logging stubs that return 0 (`DYLD_INSERT_LIBRARIES`); the launcher writes those dylibs itself, so no developer tools are needed. `tools/rosetta/run_title.py <title> --resource-root <app0> --build <x86_64 build>` wraps the launcher with a wall limit, a log file and a summary.
- **Reference title, 2026-10-11.** The guest entry is reached 0.63 s after start-up (1.8 s wall in all). The title then calls the stubbed `sceVideoOut*` and stops on `sce::Json::InitParameter2` (libSceJson2, not implemented). The TCG path takes ~1,630 s to its first draw. Next blockers: the excluded `libSceVideoOut`, `libSceAgc` and `libSceAgcDriver` (phase 3), `libSceAjm.native`, the guest-shipped `libHttpServer.Prospero`, and gaps in the libraries themselves. The first run on a new machine took 513 s before dyld failed, and the cause was not investigated. Later runs take 2–6 s.
- **Reference title with the graphics libraries, 2026-10-11.** The title now runs with real Metal submissions: guest entry 0.58 s after start-up, first flip about 8 s after launch (warm), and it keeps running (200 s checked) at about 1.2 guest flips per second. The captured frames are still near-black (no channel above 8). The fixes on the way were: `___stack_chk_guard` kept as a plain libc export for host code, macOS executable paths, unreadable `PT_DYNAMIC`, `scePthreadCancel` on joined threads, VideoOut structures on thread stacks, borrowed ranges split under `maxBufferLength`, only GPU-mapped memory borrowed, and no no-copy aliases of file-backed (image) pages, whose wiring caused a SIGBUS without an address under Rosetta. `run_title.py` lets unimplemented library functions log and return 0 (`ANYPS5_UNIMPLEMENTED=continue`), and the fault report covers SIGABRT, so uncaught host exceptions show the throw site. Open items: the borrowed direct memory (13.5 GiB, one GPU mapping) is wired whole while the GPU uses it, which leaves little memory on a 24 GiB machine; the slow flip rate and dark frames; and shaders that fail to compile (`memory_order_seq_cst`), on both paths.
- **GPU memory, shader compiles and flip rate, 2026-10-11.** A command buffer wires the host pages of every no-copy alias it uses, so guest memory is now bound per working set: captures alias only 4 MiB host granules that a binding or a GPU fault has asked for (`MetalGuestHostAliases::EnableWorkingSet`). A CPU-side miss sets the work up again, and a shader access outside the set reads zero, drops its store and reports an Unmapped fault, so the work runs again once the bytes are admitted. Over its budget (3 GiB; `ANYPS5_METAL_WORKING_SET_MIB`, 0 binds the whole mapping as before) the set starts empty. The reference title's set stays near 120 MiB, and wired memory peaks 0.6 GB above the idle baseline instead of 16 GB. The `memory_order_seq_cst` errors came from the language version: the relinked eboot declares SDK 11, whose default is MSL 2.3, while the bridge emits MSL 3.2, so converted shaders now compile as at least MSL 3.2. The flip rate was bound by the GPU queue worker, which uploaded and read back the surfaces of every draw and dispatch through the CPU (`replaceRegion`/`getBytes` inside the translated Metal driver, plus staging copies). Textures now detile straight from the snapshot mirror and blit on the GPU, and uploads no longer wait: about 10 guest flips per second instead of 1.4. The frames are still near-black.
- **UI start-up, 2026-10-11.** The reference title's UI script start-up is not blocked. Progress probes in a patched copy of its UI scripts (a symlink overlay of the resource root, kept outside the repository) show the whole sequence finishing about 25 s after launch: engine ready, 77 initial scripts loaded, components initialized, two animation frames, the out-of-box manager attached with `body` at opacity 1, the 2 s legal timeout, and then its display-settings sub-screen. A magenta page background set from the first script also never reaches the captured frames, so the UI layer is lost on the GPU side, not in a service the title polls. In steady state the title polls `scePadRead`, `sceSystemServiceGetStatus`, `sceNpGetState` and `sceImeUpdate`, all returning success (`ANYPS5_TRACE_RETURNS=1` logs return values). Skipped GPU work, per frame: a rectangle-list draw at 4× MSAA and the compute pass that then reads that 1920×1080 B10G11R11 4× MSAA image (from the first flip), and from UI start a dispatch that binds a 2048×2048 R32G32 image as one layer and as a two-layer array at the same address. Letting the rectangle-list draw run at MSAA stopped the title before its first flip, so that change was reverted. Draws whose viewport maps depth to [-1, 1] with no depth target (one per frame from UI start) now run, since Metal takes such a range, but the frames stay near-black. Directory listings now report a symbolic link as the type of its target, so a resource root laid out as links walks like the real one.
- **UI on screen, 2026-10-12.** `ANYPS5_METAL_BIND_TRACE=<flip>[:<flips>]` (off by default) logs every draw and dispatch from that presented flip on: programs, colour and depth targets, storage and sampled images (address, format, size, layers, samples, resident surface or guest memory, and for guest memory how many of 64 probed texels are non-zero), each skip and each presented buffer. Following the forced magenta page background with it showed the break: the final pass sampled an R8G8B8A8 UI layer that no draw ever wrote, because every UI draw was skipped. Their pixel shader reads per-vertex parameters (P0/P10/P20), which Vulkan feeds from a generated geometry shader and Metal could not. Metal now draws such triangle lists in two passes: the vertex shader runs as the rect-list capture kernel, and a generated vertex function draws the captured triangles, giving each corner its own outputs, its barycentric weights and the parameters of all three corners, at the locations and types the converted fragment shader declares. The reference title then shows its start-up screen (logo, legal text and middleware logos, with the display-settings sub-screen over it) from about 35 s after launch; captures reach a non-black ratio of 0.075 with 129 colours. Still skipped, and not on the UI path: the 4× MSAA rect-list depth draw, the compute pass reading a DCC-cleared 4× MSAA B10G11R11 image, and the dispatch binding one 2048×2048 R32G32 image as one and as two layers.
- **Complete start-up screens and scene inputs, 2026-10-12.** The bind trace now also logs each draw's scissor, blend and depth/stencil state and probes every written image after its copy-back. That showed UI draws that left the layer unchanged, or filled a region instead of clearing it, in a different place on every run. The guest had already rewritten the per-frame vertex and constant rings those draws read: the GPU worker ran several submissions behind it. `submit` now waits (at most 250 ms) until no more than `ANYPS5_METAL_MAX_QUEUED` submissions of the queue (default 1; negative turns it off) are waiting or running. With that, two runs ended on the same complete display-settings screen (header, the colorblind option row, its dropdown and tooltip, Continue) about 31 s after launch, instead of a different partial screen per run. The three skips behind the scene are gone: a multisampled rect-list draw builds its quad-patch pipeline at the pass sample count; a dispatch reading a 4x image no draw has rendered binds a new zero-cleared resident surface (what the first draw into it would create); and array descriptors of one allocation that name different slices bind views of one backing widened to the last slice any of them names.
- **Start-up time and CPUID, 2026-10-12.** A warm launch of the reference title spent most of its time on one thread converting SPIR-V to MSL with SPIRV-Cross, about 900 times per launch. The conversion results only lived in memory and were keyed on launch-specific values (push-constant user data, image descriptor addresses, vertex-buffer descriptors) that the generated shader does not depend on, so even within a launch about 830 of the 900 were repeats of 70 distinct shaders. `MetalConversionDiskCache` now keeps them in `<shader cache>/msl-<version>/` (LZ4, about 2 MB for this title) under a key without those values; the push-constant data is rebuilt for each caller. `ANYPS5_MSL_CACHE_VERIFY=1` converts anyway and compares (900 checked, 0 different), `ANYPS5_MSL_CACHE_STATS=1` logs hits and misses, `ANYPS5_NO_MSL_CACHE=1` turns it off. Warm launch, interleaved runs: first non-black frame 26–32 s without it, 14–15 s with it; the display-settings screen 37–43 s without, 17–18 s with. The relink was dominated by `CodeInstructionCollector` keeping every instruction start of the 100 MB eboot in a `std::set` and every visited address in hash sets: a per-segment bitmap makes it 2× faster with byte-identical output, and the launcher now runs the relinker's arm64 slice (it is built universal), so the first-launch relink fell from 36–44 s to 12–14 s and the cold first frame from 93 s to 34–45 s. The launcher also reads files with one sized read instead of a byte iterator. `ANYPS5_PROFILE_SECONDS=<n>` (libkernel, off by default) samples the running thread's program counter and a few return addresses every millisecond of CPU time for `n` seconds and prints the hottest images, host symbols, guest pages and call stacks per thread; it can perturb a title (SIGPROF interrupts system calls). CPUID: Rosetta executes FMA, MOVBE, XSAVE/XRSTOR, AVX, AVX2, F16C, BMI1/2, LZCNT and RDRAND but reports them as absent; XGETBV already returns XCR0 = 7 and leaf 0xD already describes the AVX area, while ADCX/ADOX, RDSEED, SHA, XSAVEOPT/XSAVEC and AVX-512 fault. `--to-rosetta` now sends each bare `CPUID` (26 of 27 sites in the reference eboot; the last has no room for the jump and is a leaf-0 query) to a stub that runs the real CPUID and adds those executable Zen 2 features (leaf 1 ECX, leaf 7.0 EBX, leaf 0x8000_0001 ECX ABM), preserving RFLAGS and the red zone; XGETBV sites are left alone. On this title it made no measurable difference to start-up or the settings screen's flip rate (three interleaved warm runs each).
- **Cache size caps, 2026-10-12.** Both on-disk caches are bounded. The shader cache directory (`~/Library/Caches/AnyPS5/shader_cache`: the recompiler's `ShaderDiskCache` entries, the `msl-<version>/` conversion cache and the pipeline caches) is held under `ANYPS5_SHADER_CACHE_MAX_MB` (default 1024; 0 = unlimited). Last use is the entry's mtime, refreshed on a hit at most once an hour per entry. When a write takes the directory past the cap, the least recently used entries are removed until it is under 90% of the cap (one scan at start-up, then a running byte estimate). At start-up the directories of other source versions and other MSL cache versions that no build has used for an hour are removed, since they can never hit again for this build. Entries are written to a temporary name and renamed, and read whole, so a reader that loses an entry to eviction sees a miss. The relink cache (`~/Library/Caches/AnyPS5/rosetta/<sha>/`, about 180 MB each) keeps the `ANYPS5_ROSETTA_CACHE_KEEP` (default 2; 0 = no pruning) most recently launched titles; each launch refreshes its entry's mtime and prunes the rest. The entry being launched and any entry whose `<sha>.lock` (preparation) or `<sha>.inuse` (shared lock held while the title runs) another launcher holds are never removed.
- **GPU throughput, 2026-10-12.** At the display-settings screen the guest thread waited in `WaitForQueueRoom` about 95% of the time and the GPU worker was about 99% busy, about 70% of it waiting on command buffers (`ANYPS5_METAL_GPU_TIMING=1` logs, per kind of work, the command buffers waited on, the wait and the GPU time). Each flip took about 54 dispatches, 30 draws, 70 separate copy-back command buffers and about 160 surface uploads. Copy-backs are now encoded into the work's own command buffer, and a cache of textures that still match their guest bytes (`GuestImageCache`, shared by draws and dispatches; `ANYPS5_METAL_IMAGE_CACHE=0` turns it off) skips about 57% of the uploads. It is invalidated by host range for every write the driver knows of and cleared wherever the guest may have written memory: a new submission, a flip, a rendering wait, a `WAIT_REG_MEM` that blocked or was not satisfied by the driver's own label store, EOP interrupts, sample dumps, mapping changes and failed work. The screen went from about 6.4 to about 8.8 guest flips per second (156 to 113 ms per flip) with captures byte-identical. The queue bound of #411 stays at 1: the worker is the limit, and a bound of 2 was not faster.
- **New game and map load, 2026-10-12.** The reference title now gets from its main menu through a new game's setup pages to the map loading screen, which renders its 3D leader scene. Three generic blockers were on the way. Draws had their own `MetalDevice`, so their own command queue, while dispatches used the driver's: textures shared through the image cache encoded uploads and copy-backs into the other queue's command buffer (`Metal command buffer must belong to this command queue`, then a hang at map load), and an upload pending on one queue was not ordered before a reader on the other. `MetalDraw` now draws on the driver's `MetalDevice`. Second, `submit` gave up waiting for queue room after 250 ms. A map-load dispatch that ran longer let the guest rewrite the 16-byte constant record of a queued dispatch with a tile table, and that dispatch then looped about 10⁹ times over it (a GPU hang). The wait now ends when the queue has room or its worker is parked on a host-satisfied wait (`WAIT_REG_MEM`, `RenderingWait`), with a 10 s cap that logs. The hang occurred in 4 of 4 runs before and 0 of 5 after. Third, cascaded shadow maps render each slice of a depth array as its own resident surface (`DB_DEPTH_VIEW` slice) and sample them through one 2D-array descriptor, which was skipped about 1000 times per second from the main menu on. `GatherDepthSlices` now copies the slices into an array texture on the driver's queue. A slice that no draw rendered gets the surface its first draw would create. Diagnostics: a command buffer that has not completed after 10, 30 or 60 s logs the draw or dispatch it belongs to (`GpuStallWatch`, always on). `ANYPS5_METAL_STALL_DUMP=<file>` also writes the stuck dispatch's Metal source, user data, the first words of its buffers and the buffer ranges of the previous 64 dispatches. Measured on a quiet machine (wired memory about 5 GB at start): with an empty shader cache plus a 13 s relink, the first frame came at 45 s and the display-settings screen at 48 s. With a warm cache they came at 13 s and 16 s. From a save that has already done the first-run screens, the main menu came at 28–33 s and the map loading screen at 59–64 s. On the first-run path the screen stopped flipping for about 55 s after the legal panel, while one guest thread loaded assets (guest code, Rosetta JIT, `sceKernelPread`, path resolution); shader translation was not the cost there. The loading bar then stops at 66% (checked for 330 s). The guest threads wait while the render thread draws the leader scene at 0.4–1.8 flips per second. Each 2 s window holds about 1000 dispatches and 700 draws, each its own command buffer that the worker waits on: about 1.0 s of GPU time and 1.3 s of waiting. Converting new shaders to MSL takes about 13% of the worker's samples. Still open: what the load waits for after 66%; layer and viewport index vertex exports, which are ignored, so all cascades render into slice 0; and batching draws and dispatches into fewer command buffers.
- **Draw and dispatch pipelining, 2026-10-12.** Draws and dispatches are committed without waiting (`MetalTimeline`): the worker encodes the next packet while the GPU runs, and the CPU half of each piece of work (fault check, copy of staged bytes into guest memory) runs at the next drain, in commit order. The driver drains before it reads or stores guest memory itself, before a flip, and before a CPU read of a range committed work may write; label stores and EOP interrupts behind committed work are deferred to the drain, and a submission retires (letting the guest submit past it) when its GPU work completed. `ANYPS5_METAL_DEFER=0` waits for every command buffer as before. The image cache now survives the points where the guest may have written memory: each entry proves its bytes unchanged before its next use (a hash of an uploaded surface, a 512-word sample of a GPU-written one; `ANYPS5_METAL_IMAGE_CACHE_EXPIRE=0` drops it instead), views of an array's first layers share its backing, and copy-backs cover only the levels and layers the work wrote. Converted shaders inline SPIRV-Cross's exact-arithmetic helpers under `#pragma METAL fp contract(off)` instead of calling `optnone` functions. Conversions are also kept in memory by the stable key the disk cache uses, and failed conversions and Metal compiles are remembered (`ANYPS5_MSL_CACHE_STATS=2` logs every SPIRV-Cross run). `submit`'s queue-room wait keeps waiting while the workers make progress, up to 60 s. `ANYPS5_METAL_GPU_TIMING=3` attributes GPU time to programs and surfaces. Display-settings screen, step by step: 8.8 to 13.0 (pipelining), 18.5 (inline arithmetic), 23.9 (image cache expiry), 26.3 (array views) flips per second, with captures byte-identical. A 180 s cold-cache run from launch (private shader cache, both builds stopped on the same early screen, byte-identical captures there): about 8 flips per second before and about 30 after, and SPIRV-Cross ran about 20,000 times before (43 distinct shaders) and fewer than 100 after (44).
- **Into the game, 2026-10-12.** With the main-branch changes since (shader-module cache, AGC driver sync, subgroup lane fix) the map load no longer stops at 66%: from a save that has done the first-run screens, a scripted run reaches the main menu at about 45 s, the setup pages (leader, age, civilization, settings; Square launches), the loading screen at about 150 s, an enabled Begin Game at about 275 s and the 3D map at about 300 s, then the tutorial pages and turn 1 (the "A New Home" prompt to select the founder unit). One generic blocker was on the map's way: a mip-chain pass renders one level of a mipmapped color target (bound without DCC, since the keys of mipmapped color targets are ignored) while sampling another level through a texture descriptor that names the surface's stale, cleared DCC keys. The two descriptors differed only in the DCC address, so the draw was skipped (about 1000 times a minute). Views at the same base now share one backing when they differ only in DCC metadata and both mean the same plain texels: the DCC side's keys say uncompressed, or the work writes the mipmapped target. The overlap error names the DCC keys of the side that has them. The map then shows about 4 to 8 flips per second, against about 1 before. Open: terrain missing from some presented frames, diagonal stripes over the terrain, a shadow depth texture (1024x2048, 9 levels) bound over a 1024x1024 resident depth surface and skipped, a short burst of draws whose range crosses two borrowed spans when the map first shows, and two crashes seen once each in three runs (a fault inside `CachedComputePipelineState` while building a rect-kernel pipeline, and an unsupported PM4 header 6 s after launch).
- **Map stability, 2026-10-13.** Three of the open items. Draws whose buffer crosses the boundary of two adjacent guest mappings (between 100 and 1000 skips as the map first showed) now bind: a range may cross borrowed spans that are also contiguous on the host, and the binding uses a cached no-copy "bridge" alias over those host pages (`MetalGuestHostAliases`), so nothing is copied per draw. Pipeline creation shares a reader-writer lock with additions to and writes of the Metal binary archive, which Metal does not document as safe to use concurrently, and a batch that adds nothing new (two threads built the same pipeline) no longer counts as a failed write. A submission that fails validation is read again for up to 20 ms before the error stands, since the console reads a buffer after the submit call and a title may still be finishing it; the log says whether the words changed. Neither crash recurred in 11 runs (three of them 7 minutes long, into the map); instrumented runs found no staged command buffers, REWINDs, blocked waits or command words changed between submit and execution during start-up, so the type-0 header is most likely a buffer still being written at submit. Turn 1 map: about 1 to 1.5 flips per second on a loaded machine, the same as the base build in the same conditions.
- **Map depth surfaces, 2026-10-13.** The texture skipped about 1000 times a minute from the main menu on was not a shadow map: it is a block-compressed (BC1) 1024x2048 texture the title places in memory that a 1024x1024 D16 depth target used earlier. A texture descriptor at a resident depth surface's address whose texels cannot be that plane's (block-compressed, or another texel size) now drops the dead surface and reads guest memory (`DropReplacedDepthSurfaces`); a depth-sized view still uses the surface. Depth surfaces of one depth array now share one allocation: single-sample surfaces are layers of a 2D-array texture (`MetalDepthPlanes`), a slice found later or rendered on its own moves into its array, and the array grows in place. A 2D-array descriptor over the slices is a view of those layers rather than a copy, and a depth-only draw that exports a render target index renders slices `SLICE_START..SLICE_MAX` (`DB_DEPTH_VIEW`) in one layered pass. On the title's map the shadow draws do not need it: the menu's leader scene renders its three 1024x1024 cascades slice by slice, and the map renders one 2048x2048 D32 depth target. With these changes no draws or dispatches are skipped from the menu to turn 1 (before: 1000 to 9999 of these in one run, 10 in another). Still open: diagonal stripes over the map's terrain and fog. Replacing the 2048x2048 depth texture that map draws sample with a cleared one leaves them unchanged, so they do not come from that texture. Terrain missing from presented frames was not seen in about 100 map frames captured at 5 s intervals over five runs.
- **Map stripes, 2026-10-13.** The stripes came from the map's shadow moment pass, a compute dispatch that reads the 2048x2048 D32 shadow depth and writes a two-layer RG32F texture. Rows 12 to 15 of every 16-row tile of that texture were zero straight after the dispatch, which is the fourth wave64 wave of each 16x16 workgroup. That wave has no lanes in the shader's 9x9 LDS fill, so it skips the fill (`s_cbranch_execz`) and meets the others at the `s_barrier` after it. Inside the fill, the converter orders each guest wave's LDS accesses across host invocations with `OpControlBarrier` at subgroup execution scope, but SPIRV-Cross widened that to the workgroup memory scope and emitted `threadgroup_barrier`, which the skipping wave never reached; the barriers paired with its `s_barrier` and it read LDS before the other waves wrote it. The Metal bridge now emits `simdgroup_barrier` for subgroup-scope control barriers. A guest replay fixture reproduces the pattern (a wave that skips the LDS writes read zeros, and now reads the written values).
- **The queue bound's cost, 2026-10-18.** With the replay measuring the live-map frame as worker plus GPU, `WaitForQueueRoom` looked like the lever: on the reference title's map frame the guest thread sits in `SubmitCommandBuffer` for 429-461 ms of a 428-454 ms frame at the default `ANYPS5_METAL_MAX_QUEUED=1`, 378-436 ms at 2, 290-324 ms at 4 and 225-232 ms at 8 (M5 Pro, K=5 timed repeats, two interleaved rounds, load 3.7-8.6, `ANYPS5_REPLAY_NO_PIXELS=1`). The frame itself does not move: 428/454, 423/464, 420/459 and 435/447 ms wall for 1, 2, 4 and 8, with worker CPU 240/254, 244/259, 268/269, 280/270 ms and GPU busy 161/160, 156/196, 156/191, 169/197 ms. A deeper bound only moves where the guest waits, into the driver's own waits, and costs worker CPU (more work in flight to materialize and drain); the frame is the worker's encode plus the GPU work it waits on, and the guest's submit wait is that pipeline's latency. The bound stays at 1, and what a capture would have to hold is why: at submit the driver copies the command words (`CaptureSubmissionCommands`), the indirect register lists, the shader registry and the flip and rendering-wait outputs, and nothing of the memory those commands read. Vertex and constant rings are read at execution, and the map-load hang above came from a queued dispatch reading a *tile table* through a GPU address, so a capture that made a deeper bound safe would have to cover the whole guest arena, not the declared rings. The frame lever is the worker-to-GPU pipeline (parallel encoding, fewer encoders, less GPU work), not the bound.
- **Tests.** `ctest -L rosetta` in an x86_64 `-DANYPS5_ROSETTA_LIBS=ON` build needs `ld.lld`. It builds small guest fixtures from [`tools/rosetta/tests`](../../tools/rosetta/tests), relinks them and runs them under `arch -x86_64`. ## 6. The TCG path is gone

Direct execution is the only engine. The QEMU/TCG runner (`anyps5_cpu_run`, `core/cpu`) and the Unicorn and AnyPS5-TCG submodules were removed; the pointer translation and loader that were TCG-only went with them. The Metal backend, `core/libs` and the x86_64 library build are what remains, and CI keeps the shader bridge, guest replay and Rosetta jobs. The TCG numbers in sections 1 to 5 are the spike's historical comparison.

## 7. Input

- **Keyboard and mouse.** They reach the native AppKit window, not SDL. The main-queue pump in `DirectDisplayWindow.mm` drains the window's events and publishes them to `libSceKeyboard` and `libSceMouse`. It also pushes key presses and focus loss into SDL's event queue, where the presentation thread's `PadInput` maps them to pad buttons through the usual bindings (`anyps5-input.ini`; Space and Return are Cross by default). Before this, keys never reached the pad on the direct path. `rosetta_direct_input` posts a Space key to the window and reads Cross back through `scePadReadState`.
- **Controllers.** They go through SDL's game controller support, which stays initialized on the offscreen video driver, as on the SDL window.
- **Scripted presses.** `ANYPS5_INPUT_SCRIPT` presses buttons at fixed times through the same pad state the title reads, for agents and CI. It is off unless set, and adds to live input. The format is `t=<seconds since process start>:<button>[+<button>...][:<hold ms>]`, with entries separated by `;`. The default hold is 250 ms. The hold counts from the first pad read that sees the press, so a title that polls slowly still sees each press. Each press logs `[pad] input script ...: down at <s> (epoch ms <ms>)`, which lines up with `ANYPS5_FRAME_CAPTURE_DIR` file names. For example: `ANYPS5_INPUT_SCRIPT="t=42:square;t=56:square;t=66:cross"`. Button names: cross, circle, square, triangle, up, down, left, right, l1, r1, l2, r2, l3, r3, options, touchpad.
- **Skipping intro movies in test runs.** There is no skip-movies switch, on purpose. A title that plays its logo and intro movies through `libSceAvPlayer` or `libSceVideodec2` goes through our HLE, where a skip could end playback like a finished movie. A title that decodes them itself on the guest CPU (a bundled WebM/VP9 decoder module, with no AvPlayer or Videodec import) gives us no boundary to hook, and we do not patch title code. Check the title's imports and bundled modules first. For the second kind, start `ANYPS5_INPUT_SCRIPT` early and press every 3 s: such movies and the first-run screens usually end on the release of an accept, cancel or action button, so alternating `cross` and `square` from `t=8` clears them as soon as the title reads the pad. One measured title reached its main menu at about 73 s this way, against about 130 s with presses starting at `t=46`.

## 8. Save data and shutdown

**Where a title's data lives.** The title runs with its relink-cache `out/` directory as its root, and writes `_sd/` (libSceSaveData, one folder per save directory name) and `download0/` (the title's own option files) there. The launcher now links both to one directory per title, outside the relink cache, so they survive a re-relink, a patched eboot and a cache wipe:

| Guest path | Host path |
| --- | --- |
| `_sd/<dirName>` | `<data>/SaveData/<dirName>` |
| `download0/...` | `<data>/download0/...` |

`<data>` is `--data-dir DIR`, else `ANYPS5_TITLE_DATA`, else `~/Library/Application Support/AnyPS5Launcher/TitleData/<titleId>` (the title id is read from `sce_sys/param.json`; a title without one keeps its data in the cache). That is the folder the MacPS launcher already used per title, with the same `SaveData` and `download0` names. Data a title already wrote into the cache is moved in on the first run; a file already in the data directory wins. Every save write goes straight to disk through a temporary file and a rename, so a stop never leaves a half-written save.

**Ending the game.** Closing the window, Cmd-Q, SIGTERM (the launcher forwards MacPS's stop), SIGINT and SIGHUP all call `EndDirectSession`: it marks the exit as requested (guest threads that meet the shutdown park instead of unwinding into guest frames), runs the libc shutdown callbacks (the video output and GPU threads stop and join), flushes stdio and exits with code 0. A watchdog thread leaves with code 0 after one second whatever the callbacks are doing, which is inside the launcher's 1.5 s grace before SIGKILL. A title that calls `exit` itself takes the existing `LibcExit` path.

## 9. Audio

**What the reference title does.** It plays everything through one AudioOut2 context (512-sample grains, queue depth 4) with one 8-channel port, from a middleware sink built of two guest threads. A renderer thread waits on an event flag, renders grains only while `sceAudioOut2ContextGetQueueLevel` reports room, and hands each grain to a push thread through a semaphore. The push thread calls `sceAudioOut2ContextPush` with blocking set, then sets the renderer's event flag. Nothing in the sink wakes the renderer on a timer; the only other waker is the game's frame loop.

**Why the audio kept cutting out.** A blocking push returned as soon as the grain was queued. The renderer filled the queue, found no room and slept, and with no push left to block nobody woke it until the game's next frame tick. At the title's frame rate on this path (often under one per second, seconds apart while loading) it produced 2 to 11% of real time: bursts of a few dozen grains, then seconds of silence. A blocking push now returns once the queue has room for the next grain, so the push thread wakes the renderer at the output rate, as it does on the console. `audio_out2_pacing` models the sink with host threads and a 2 Hz frame loop: before the change, 3 s of audio took 17 s to hand over with 34 cuts of about 400 ms; after it, 3.2 s and none.

**Jitter buffer.** The device starts playing once a cushion of 40 ms is queued, and the title's queue sits on top of it. When the device runs dry anyway because the renderer was descheduled (Rosetta, the GPU worker, other processes), the next push grows the cushion to cover a gap like the one that caused it, up to 200 ms; gaps over 250 ms are outages and are left alone. After 10 s without running dry it shrinks again by 10 ms steps. The thread that pushes is raised to the interactive QoS class on its first push, since guest thread priorities are not mapped to the host.

**Counters.** `ANYPS5_AUDIO_STATS=1` prints, every 10 s per AudioOut2 context: pushes against the number the output rate expects, the longest gap between pushes, the time pushes blocked, full-queue timeouts, underruns and the silence they played, dropped grains, the queued audio range, the current cushion, the device callbacks and the pushing thread's id (to find it in `sample`). AJM adds a line per 10 s with batches, decode runs, frames, invalid-data and no-room results, and the decode time. `APS5_TRACE_AUDIOOUT2=1` and `APS5_TRACE_AJM=1` still trace individual calls, and `APS5_TRACE_SYNC=1` now also logs the caller of each event flag set.

**Measured (reference title, scripted input from a save through the menus, the map load and onto the map, 480 s runs).** Before: the title pushed 2% of real time in the menus, 1% during the map load and 10% on the map, so the output was silent 98%, 99% and 90% of the time, with 17, 8 and 69 underruns per minute. After: 100% of real time in every phase; 5 underruns in 8 minutes (about 2 per minute in the menus, 0.4 per minute during the map load, none on the map), under 1% silence in any phase, no dropped grains, and the cushion back at 40 ms on the map. AJM decode stayed under 2% of wall time with no decode errors in either run, so decoding was never the bottleneck.
